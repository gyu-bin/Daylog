## Findings resolved in follow-up

### Resolved P2 — joined entitlement refresh can report failure before the successful retry

`Daylog/Services/PioPurchaseManager.swift:234` returns the raw in-flight task result to coalesced callers. A verified update arriving while that task reads the ledger invalidates its revision and makes it return false at line 242. Only the original caller reaches the retry at line 265. A Restore operation joining that refresh can therefore show a failure even though the original caller immediately retries and recovers verified ownership. All callers should await the same complete refresh/retry operation or follow the same revision retry rule. Add a held snapshot + transaction update + overlapping restore regression case.

### Resolved P2 — a revoked transaction removes every entitlement for its product

`Daylog/Services/PioPurchaseManager.swift:318–320` removes ownership by outfit and immediately repairs the saved equipped selection, without considering transaction identity or a replacement entitlement. If an older refunded transaction is delivered/replayed after a verified repurchase of that product, the newer valid purchase is incorrectly locked and the selected preference is overwritten. Reconcile revocation against verified current entitlements, or retain authoritative active transaction identities, before permanently repairing the selection. Add a refund/rebuy/late-old-update regression case. This is an entitlement ordering issue, not evidence that an unverified payment can unlock content.

### Resolved P2 — global review host uses normal device preferences

`DaylogStoreKitTests/PioGlobalReviewView.swift:40` injects `DevicePreferences.shared`. That singleton uses `UserDefaults.standard` (`Daylog/Models/DevicePreferences.swift:7,50`). Consequently this review action can persist the normal application's welcome-dismissal preference even though routine data is in memory and wardrobe selections use an isolated suite. Inject a DevicePreferences instance backed by a dedicated test suite into this test-only host. This is a test-harness preference-isolation defect, not a cloud-record or entitlement bypass. No evidence is asserted that the QA session actually clicked this button. Parent notified; reviewer made no app/test changes and ran no builds/tests.
