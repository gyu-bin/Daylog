# Daylog 전체 기능 점검 (Phase 6-D)

- 점검일: 2026-10-13
- 기준 커밋: `dfd53e6` (Mac 1.5.3 (3), iOS 1.0.0 (7)이 배포된 상태의 `main`)
- 방법: 코드에서 기능 목록을 만든 뒤, 실제 앱을 조작해 하나씩 확인했다. 코드만 읽은 항목과 실제로 조작한 항목을 구분해 적는다.
- 이번 작업에서 배포한 것은 없다(TestFlight 업로드, GitHub Release, 설치된 앱 교체 모두 하지 않음).

## 판정 기준

| 판정 | 뜻 |
|---|---|
| `PASS` | 이번 점검에서 실제 앱을 조작해 정상 동작을 확인했다 |
| `FAIL` | 실제 조작에서 결함을 확인했다(이번에 고친 것은 "FAIL→수정"으로 적고, 고친 뒤 다시 조작해 확인한 결과를 함께 적는다) |
| `PARTIAL` | 일부만 실제로 확인했다(무엇을 못 했는지 근거 칸에 적는다) |
| `CODE_ONLY` | 코드와 단위 테스트로만 확인했다. 이번 점검에서 실제 조작은 하지 않았다 |
| `BLOCKED` | 이 환경에서는 조작할 방법이 없었다 |
| `NOT_IMPLEMENTED` | 구현돼 있지 않다 |

## 점검 환경

| 환경 | 내용 |
|---|---|
| macOS | macOS 27.0.1, Xcode 27.0. 검증 전용 빌드(`com.daylog.verify`, Debug, iCloud 없음, 별도 저장소 `qaD1`). 창을 앞으로 가져오지 않는 배경 제어로 조작 |
| iPhone | iPhone 17e 시뮬레이터(iOS 27.0, 가장 좁은 화면). 저장소 `qaP1`·`qaN1`·`qaO1` |
| iPad | iPad Pro 11 시뮬레이터(iOS 27.0, 세로). 저장소 `qaI1` |
| 건드리지 않은 것 | `/Applications/Daylog.app`(1.5.3)과 그 저장소, 운영 iCloud 데이터, TestFlight 빌드 |

환경에서 오는 한계(아래 표의 `BLOCKED`·`PARTIAL`의 원인):

- 시뮬레이터에는 iCloud가 없다. 동기화·기기 목록·병합 안내는 실제 조작으로 확인할 수 없다.
- macOS 배경 제어는 메뉴 단추(⋯), 오른쪽 클릭 메뉴, 끌어서 놓기, Return 키, 시스템 파일 창을 다루지 못한다. 메뉴 막대 명령은 실행할 수 있다.
- 시뮬레이터 도구는 끌어서 놓기를 시작하지 못하고, 회전을 못 하며, 글자 입력(붙여넣기)이 Mac 클립보드와 섞여 믿을 수 없었다. 글자를 넣어야 하는 화면은 macOS에서 확인하거나 디버그 스크립트로 값을 넣고 화면에서 결과를 확인했다.
- 홈 화면에 위젯을 올리는 조작을 하지 못했다.

## 3. 판정 집계와 실제 확인 비율

구현된 기능 113개(§1 표의 번호 매긴 항목) 기준이다. 구현되지 않은 항목 2줄(전체 백업 복원, macOS·잠금 화면 위젯)은 따로 적었고 계산에서 뺐다.

| 판정 | 개수 | 비율 |
|---|---|---|
| PASS(이번에 실제 조작으로 확인) | 71 | 63% |
| PARTIAL(일부만 실제 확인) | 12 | 11% |
| CODE_ONLY(코드·단위 테스트만) | 22 | 19% |
| BLOCKED(이 환경에서 조작 불가) | 8 | 7% |
| 합계 | 113 | 100% |

- **실제로 확인한 비율: 71/113 = 63%.** 일부만 확인한 것까지 넣으면 83/113 = 73%다. 코드 검토만 한 22개와 조작하지 못한 8개는 확인한 것으로 세지 않았다.
- PASS 중 3개(#13, #59, #96)는 처음 조작에서 결함이 나와 고친 뒤 다시 조작해 통과한 것이다. 고치지 못하고 남은 FAIL은 없다.
- PASS는 "한 플랫폼 이상에서 실제 조작으로 확인"을 뜻한다. 괄호 안에 적지 않은 플랫폼에서는 같은 기능을 확인하지 않았다. 특히 iPad는 표본만 봤다(§2).
- CODE_ONLY 가운데 #44, #49, #50, #65, #102, #111, #112는 이전 단계(6-A·6-B·6-C)에서 실제로 확인한 적이 있지만, 이번 점검에서 다시 조작하지 않았으므로 PASS로 세지 않았다.

## 4. 실제로 발견한 결함, 재현 방법, 수정

### 4-1. 알림의 [완료]를 누르면 앱이 충돌한다 (P1, 수정함)

- 재현: iPhone에서 시간이 있는 루틴을 만들고 알림을 허용한다 → 앱을 홈 화면으로 내려 둔다 → 알림이 오면 배너를 내려 [완료]를 누른다.
- 결과: 완료 기록은 저장되지만 앱이 곧바로 끝난다(`NSInternalInconsistencyException: Call must be made on main thread`). 충돌 보고서가 남고, 위젯에 넘기는 데이터가 갱신되지 않아 위젯에는 미완료로 남으며, 알림 다시 예약도 건너뛴다.
- 원인: `AppRuntime`의 `userNotificationCenter(_:didReceive:)`를 `async` 꼴로 받았다. 이 꼴은 시스템의 완료 블록을 메인 스레드 밖에서 부르고, 앱이 뒤에 있을 때 UIKit이 그 자리에서 앱을 끝낸다.
- 수정: 완료 블록을 받는 꼴로 바꾸고, 처리와 완료 블록 호출을 메인 스레드에서 한다(`AppRuntime.respond(action:routineID:dateKey:completion:)`).
- 회귀 테스트: `NotificationActionTests.respondingOffTheMainThreadFinishesOnTheMainThread`.
- 수정 후 실제 확인: 같은 절차로 [완료] → 앱이 같은 프로세스로 살아 있음, 새 충돌 보고서 없음, 위젯 데이터가 완료로 바뀜.
- 영향 범위: **이미 배포된 TestFlight 1.0.0 (7)과 Mac 1.5.3에는 이 수정이 없다.** 기록이 사라지지는 않지만 iPhone에서 알림의 [완료]를 쓸 때마다 앱이 끝난다. 다음 빌드에 넣어야 한다.

### 4-2. 빠른 추가([+], ⌘N)가 아무 일도 하지 않는 경우 (P2, 수정함)

- 재현: (가) 오늘이 휴가인 날, (나) 마지막으로 쓴 그룹에 오늘 예정된 루틴이 없는 날(예: 주말 전용 그룹), (다) 오늘 화면에서 루틴 카드를 숨긴 상태 → [+] 또는 ⌘N.
- 결과: 입력 칸이 열리지 않고 화면도 바뀌지 않았다.
- 원인: 오늘 화면에 그 그룹의 입력 칸이 없는데도 오늘 화면에 머물렀다.
- 수정: 오늘 화면에 그 그룹의 입력 칸이 없으면 루틴 관리 화면으로 가서 그 그룹의 입력 칸을 연다(`AppStore.requestQuickAddFocus(dashboardShowsRoutines:)`, `dashboardCanAdd(to:)`, `pendingQuickAddGroupID`).
- 회귀 테스트: `RoutineManagementTests.quickAddGoesToRoutineManagementWhenTheDashboardHasNoField`.
- 수정 후 실제 확인: 휴가인 날 [+] → 루틴 관리로 이동. 평소 날은 전처럼 오늘 화면의 입력 칸이 열림. 지난 날짜를 보던 중 ⌘N → 오늘로 돌아와 입력 칸이 열림.

### 4-3. 전체 기록 JSON을 가져오기로 고르면 엉뚱한 안내가 나온다 (P3, 수정함)

- 재현: 설정 → 데이터 → [전체 기록 JSON]으로 저장 → [파일 선택…]에서 그 파일을 고른다.
- 결과: "루틴 JSON의 필드와 자료형을 확인해 주세요. version은 정수, weekdays는 정수 배열이어야 해요." 데이터는 바뀌지 않는다(거부 자체는 안전).
- 원인: 형식을 보기 전에 파일을 통째로 풀었다. 전체 기록 파일에는 `routines`가 없어 자료형 오류로만 보였고, 준비해 둔 "전체 백업 JSON은 복원할 수 없어요" 안내에 닿지 못했다.
- 수정: 형식부터 본다(`RoutineTransferFormat.decode`).
- 회귀 테스트: `RoutineTransferTests.fullBackupFileIsRejectedWithARestoreMessage`.
- 수정 후 실제 확인: 같은 파일 선택 → "지원하지 않는 JSON 형식 또는 버전이에요. 전체 백업 JSON은 복원할 수 없어요."

### 4-4. 설정의 카드 목록에서 순서 단추가 엉뚱하게 동작할 수 있다 (P3, 수정함, 화면 재현은 못 함)

- 조건: 이 기기에 내용이 없는 카드(다른 기기에서 지운 텍스트 카드 등)가 순서에 남아 있을 때, 좁은 화면의 설정 → 오늘 화면 카드 목록.
- 결과(코드 검토): 위·아래 단추가 보이지 않는 카드와 자리를 바꿔 눌러도 변화가 없고, 마지막 줄의 아래 단추가 켜져 있다.
- 수정: 목록에 보이는 카드끼리 자리를 바꾼다(`DevicePreferences.move(_:by:among:)`).
- 회귀 테스트: `DevicePreferencesTests.movingAmongListedCardsSkipsCardsThatAreNotListed`.
- 이 조건은 다른 기기의 삭제가 동기화돼야 생기므로 시뮬레이터에서 화면으로 재현하지 못했다.

### 4-5. 편집 시트가 떠 있을 때 메뉴 명령이 화면을 바꿔 시트가 닫힌다 (P2, Codex 지적 → 재현 → 수정함)

- 재현(4-2를 고친 직후의 코드): macOS에서 오늘이 휴가인 날 → 오늘 화면의 [유지할 루틴 고르기]로 휴가 편집 시트를 연다 → 메뉴의 파일 → 새 루틴 항목(⌘N).
- 결과: 화면이 루틴 관리로 바뀌면서 시트가 닫혔다. 시트에 적던 내용은 저장되지 않는다. 4-2의 수정이 ⌘N에 화면 전환을 새로 넣으면서 생긴 문제이고, 화면 이동 명령(⌘1…⌘8)에는 전부터 같은 문제가 있었다.
- 수정: 시트가 떠 있으면 ⌘N과 화면 이동 명령이 아무것도 하지 않는다(`Platform.isShowingSheet`, `AppStore.requestQuickAddFocus(…isShowingSheet:)`, `AppStore.go(to:isShowingSheet:)`).
- 회귀 테스트: `RoutineManagementTests.menuCommandsDoNotSwitchScreensUnderASheet`.
- 수정 후 실제 확인(macOS): 시트를 연 채 "새 루틴 항목"과 "이동 → 통계"를 눌러도 시트가 그대로 남음. 시트를 닫은 뒤에는 명령이 전처럼 동작.
- 같은 문제의 iPad 경로(Codex 2회차 지적, **재현하지 못함**): iPad에서 창을 두 개 열면 두 창이 같은 화면 선택을 따른다. 한 창에 편집 시트가 떠 있을 때 다른 창의 [+]를 누르면 같은 일이 생길 수 있다. 화면의 [+]도 같은 보호를 받게 하고, iPad·iPhone에서는 모든 창의 시트를 보도록 했다. 시뮬레이터 도구로 창을 두 개 만들 수 없어 이 경로는 코드로만 확인했다(`CODE_ONLY`). 한 창에서 [+]가 전처럼 동작하는 것은 다시 조작해 확인했다.
- 남은 것(전부터 있던 동작, 이번에 바꾸지 않음): iPad의 두 창에서 사이드바·탭으로 화면을 바꾸면 다른 창의 시트도 닫힌다. 화면 선택을 창마다 따로 두는 것은 구조 변경이라 별도 작업이다.

### 4-6. 다른 화면에서 ⌘N을 누르면 오늘 화면으로만 가고 입력 칸이 열리지 않는다 (P3, 수정함)

- 재현(macOS, 넓은 화면): 통계 화면에서 파일 → 새 루틴 항목(⌘N).
- 결과: 오늘 화면으로 바뀌지만 "항목 추가" 칸이 열리지 않았다(한 번 더 눌러야 열렸다). 전부터 있던 동작이다.
- 원인: 오늘 화면의 루틴 카드는 화면이 바뀔 때 새로 만들어져, 그 전에 온 요청 신호를 보지 못했다.
- 수정: 다른 화면에서 온 요청을 남겨 두었다가 루틴 카드가 나타날 때 입력 칸을 연다(`AppStore.pendingDashboardQuickAdd`). 오늘 화면을 떠나면 요청을 버린다.
- 회귀 테스트: `RoutineManagementTests.quickAddGoesToRoutineManagementWhenTheDashboardHasNoField`에 단언 추가.
- 수정 후 실제 확인: 통계 화면에서 ⌘N → 오늘 화면의 마지막으로 쓴 그룹에 "항목 추가" 칸이 열림. 다른 화면에 다녀와도 다시 열리지 않음.
- 남은 것: 그룹이 하나도 없을 때 통계 같은 다른 화면에서 ⌘N을 누르면(넓은 화면) 루틴 관리로 가지만 새 그룹 칸은 열리지 않는다(오늘 화면이나 iPhone에서는 열린다). 드문 경우라 고치지 않았다.

### 결함이 아니라고 확인한 것

- 식사 기록 줄의 도움말 "대시보드에서 이 날짜의 식사를 보고 고칩니다": 실제로 대시보드를 그 날짜로 연다.
- 통계의 평균이 낮게 보이던 경우: 만든 당일에 지운 루틴의 미완료 체크가 그날 기록에서 빠지는 규칙 때문이며 손 계산과 일치했다.
- `daylog://today`가 밖에서 열리지 않는 것: 시스템에 등록한 주소가 아니라 위젯 전용 링크다.

## 7. 데이터·CloudKit 안정성 평가

실제로 확인한 것:

- 저장 → 종료 → 재실행을 날짜를 바꿔 가며 10회 넘게 반복했고 기록이 유지됐다(체크, 건너뛰기, 식사, 휴가, 대시보드 카드).
- 루틴·그룹을 고치거나 지워도 지난 날짜의 이름·상태·통계가 바뀌지 않았다. 삭제는 행을 남기는 소프트 삭제다(건수로 확인).
- 가져오기(CSV·템플릿)는 추가만 하고 기존 기록을 바꾸지 않았다. 잘못된 파일은 저장 없이 거부됐고, 넘긴 원본 파일은 지워지지 않았다.
- 내보낸 전체 기록 JSON의 엔티티 건수가 저장소와 일치했다.
- 알림 [완료] 충돌(§4-1)에서도 완료 기록은 저장돼 있었다. 잃은 것은 위젯 갱신과 알림 다시 예약이었다.

실제로 확인하지 못한 것(코드와 단위 테스트로만 확인):

- **iCloud 다중 기기 동기화**: 시뮬레이터와 검증 앱에는 iCloud가 없고 별도 시험용 컨테이너도 없다. 같은 날 다른 기기의 체크 병합(`CheckSyncTests`), 같은 칸 동시 수정(`ConcurrentFieldEditTests`), 들어온 변경 반영(`IncomingChangeTests`, `SyncReconcilerTests`), 저장소 다시 올리기(`StoreReseedTests`) 테스트가 통과하는 것까지만 확인했다. 실기기 PASS가 아니다.
- 앱을 켜 둔 채 자정을 넘기는 것, 시간대를 바꾸는 것, 오프라인에서 고친 뒤 다시 연결하는 것.
- 운영 저장소(실제 설치 앱)는 열지 않았다.

평가: 이번 점검에서 기록이 사라지거나 값이 틀리는 결함은 찾지 못했다. 가장 큰 위험은 여전히 실기기 두 대 이상에서의 동기화가 사람 손으로만 확인된다는 점이다. `DaylogReuploadAll` 실행 인자는 릴리스 빌드에서도 동작하지만 명시적으로 줘야 하고 백업 뒤 환경당 한 번만 실행된다(의도된 운영 도구로 판단, 변경하지 않음).

이번 수정은 스키마, CloudKit 구조, 저장 형식을 바꾸지 않는다.

- iPhone·iPad에서 알림 창·말풍선이 떠 있는 동안 명령이 잠깐 막힐 수 있다(닫히면 풀린다).
- 알림 테스트는 시스템이 실제로 부르는 경로가 아니라 도우미 함수를 시험한다 → 실제 경로는 시뮬레이터에서 조작으로 확인했다(§4-1).

1. 2회차 지적을 고친 변경(화면의 [+]에 보호 적용, iPhone·iPad에서 모든 창의 시트 확인).
2. 그 확인 과정에서 찾은 §4-6의 수정(`pendingDashboardQuickAdd`).

두 변경 모두 전체 테스트와 빌드, 실제 조작(macOS·iPhone·iPad 한 창)으로 확인했다. iPad 두 창 경로만 조작으로 확인하지 못했다.
